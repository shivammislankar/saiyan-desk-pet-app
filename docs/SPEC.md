# Goku Desktop Pet — Master Specification

**Electron + TypeScript + Canvas | Windows and macOS | Open source (MIT)**

## 0. How to Use This Spec

This document is the authoritative specification for the Goku Desktop Pet project. Work through it one phase at a time (section 26). Do not try to implement everything in one pass.

**First-run prompt:**

> Create the repository at `D:\Projects\saiyan-desk-pet` (follow section 0.1: nothing on the C: drive and nothing inside OneDrive). Save this specification as `docs/SPEC.md`. Read it fully. Complete the "How to start" steps in section 26 and implement Phase 1 only. Follow the status rules in section 27. When finished, update `docs/implementation-status.md` and `docs/manual-verification-checklist.md`, then stop and report what was written, built, executed and verified. Do not begin Phase 2.

**Prompt for each later phase:**

> Read `docs/SPEC.md`. Phase N-1 is complete. Implement Phase N only, following the sections it lists. Follow the status rules in section 27. Update the status and checklist documents, report exactly what was written, built, executed and verified, and stop. Do not begin Phase N+1.

Hard rules that apply to every phase:

- The privacy contract (section 10), the legal and asset rules (section 3) and the security rules (section 23) are never relaxed.
- If something in this spec conflicts with the actual behavior of Electron, an OS or a dependency, document the conflict in `docs/decisions.md` and choose the closest safe behavior.

### 0.1 Project Location and Drive Rules (Windows)

- **Project root:** `D:\Projects\saiyan-desk-pet` (short path, no spaces).
- **Build output** goes to `<project>\release\` (git-ignored).
- **Dependency caches** go to `D:\dev-cache\npm`, `D:\dev-cache\electron`, `D:\dev-cache\electron-builder`.
- **Development data directory:** `D:\Projects\saiyan-desk-pet-data` (sibling folder, outside the repository).
- **Packaged app data:** `%APPDATA%` by default; `portable.flag` next to the executable enables portable mode.
- **Private source art** is kept outside the project folder, e.g. `D:\goku-private-art\`.

## 1. Non-Negotiable Technology Requirements

### Required stack

- **Electron** for native desktop windows, application lifecycle, tray, IPC and OS integration.
- **TypeScript** with strict type checking.
- **HTML Canvas 2D** for rendering pixel art, animation frames, particles, auras, speech bubbles and effects.
- **Node.js** for filesystem access, configuration, the local HTTP server, timers and application services.
- **uiohook-napi** for global keyboard, mouse and scroll events (Phase 2+).
- **active-win** for best-effort active-window detection and Peek mode (Phase 4+).
- **electron-builder** for Windows and macOS packaging.
- **Vitest** for testing.
- **Zod** for schema validation.
- **ESLint** and **Prettier**.

### Absolutely prohibited

- Godot, GDScript, Unity, Unreal Engine.
- Phaser, PixiJS or another game engine.
- A browser-only website pretending to be a desktop pet.
- A simulated desktop inside a normal application window.
- Remote web applications or hosted rendering services.
- Unnecessary external APIs, telemetry or analytics.

## 2. Product Vision

An original pixel-art Goku desktop companion who lives on top of normal desktop applications. He hovers and flies, reacts to input, performs combat animations, rides a Flying Nimbus, responds to productivity timers, and reflects AI coding-agent activity.

## 5. Electron Windows and Desktop Behavior

### 5.1 Goku sprite window

- Transparent, frameless, always-on-top Electron window.
- No title bar, transparent background, no scrollbars.
- No focus stealing during normal animations.
- No taskbar or Dock entry for the pet window.
- Secure: `contextIsolation: true`, `nodeIntegration: false`, sandbox enabled.
- Narrow typed preload API. No unrestricted IPC forwarding.
- Restrictive Content Security Policy.

### 5.2 Click-through and sprite hit testing

- Desktop remains interactive everywhere except visible character pixels.
- Clicking and dragging visible character pixels works.
- Fully transparent regions pass through.
- Correct hit testing when animation changes or Goku faces the other way.
- Ordinary clicks pass through to applications.
- Restoring click-through after interaction ends.

### 5.3 Effects overlays (created on demand)

- Transparent click-through overlay windows, one per display, created only when needed.
- No overlay window exists while idle. Create on effect start, destroy after effect finishes.
- Track display changes. Use logical display coordinates.
- Never steal focus or intercept clicks.

## 6. Movement and Physics

### 6.1 Default floating behavior

- Gentle sine-wave vertical bobbing, slight horizontal drift, flying poses, subtle ki glow.
- Smooth acceleration and deceleration, direction-aware movement and facing.
- Stable resting positions, optional bounded idle wandering.
- Wherever the user drops him, he stays there and hovers.
- No default gravity, ground collision, walking cycle, falling animation or floor bounce.

### 6.2 Dragging and throwing

1. Enter dragging state.
2. Lift him by the gi visually.
3. Track pointer movement, estimate release velocity.
4. On release, preserve throw velocity, apply smooth air friction, settle into hover.
5. Rapid direction changes produce wobble.

### 6.3 Optional Gravity (off by default)

Configurable gravity, falling, landing detection, return to hover.

### 6.4 Physics implementation

- Delta-time-based integration.
- Stable damping (exponential velocity decay).
- Clamp extreme delta times.
- Simulation state separate from rendering state.
- Centralized constants.

### 6.5 Multi-monitor persistence

- Persist position relative to selected display (normalized coordinates plus display identifier).
- On restart: prefer original display, otherwise choose sensible available one.
- Clamp to visible work-area bounds.

## 7. Canvas Renderer

- Canvas 2D with integer scaling and nearest-neighbor rendering.
- `imageSmoothingEnabled = false`.
- Layered rendering: sprite, aura, particles, speech bubbles, Nimbus, status effects.
- Bounded particle and afterimage system.
- Target 60 FPS during active animation, under 3% idle CPU.
- `requestAnimationFrame` for visible rendering. Avoid work when scene is static.

### 8.1 Required actions

`idle`, `fly`, `hover`, `nimbus_ride`, `punch_1`, `punch_2`, `punch_3`, `kick_1`, `kick_2`, `uppercut`, `block`, `kamehameha_charge`, `kamehameha_fire`, `kaioken`, `laugh`, `scroll_unroll`, `peek`, `stretch`, `drink`, `thinking`, `done`, `drag`, `sleep`.

### 8.2 Per-action schema

Sheet path, frame width/height, total frame count, frames per row, FPS, anchor coordinates, looping behavior, optional frame events, optional directional-flip behavior.

### 8.3 Pack import tool

`npm run import-pack <source-folder> [--map map.json] [--name <pack-name>]`

Supports: folder of individual PNG frames, single grid sprite sheet, Shimeji-style folder.

## 9. Animation Controller, Layers and Priorities

### 9.1 Layered model

1. Body layer: movement pose.
2. Action layer: strikes, Kamehameha, reminders, mouse reactions.
3. Status layer: ambient AI-agent state.

### 9.2 Priority policy (highest first)

1. Direct user interaction: drag and release.
2. Kamehameha sequence.
3. Required system feedback.
4. Reminder presentations, one-shot agent reactions.
5. Keyboard strikes, Kaioken, mouse reactions.
6. Ambient agent status.
7. Idle behavior.

### 9.3 Request contract

Action name, priority, duration/completion condition, loop flag, interruptible flag, movement allowed, facial overrides allowed, completion callback.

## 10. Global Input and Privacy

### 10.1 Absolute privacy rules

- Never record typed text or store which keys were pressed.
- Never log raw key codes.
- Never send raw input events to renderer, localhost server or external services.
- Never use global hooks to capture passwords, clipboard or unrelated activity.
- Never add telemetry or analytics.
- Never suppress or modify ordinary OS keyboard shortcuts.

### 10.2 Enforced privacy invariants

- Import restriction (ESLint rule).
- Type-level guard.
- Invariant test.
- CI check script.
- `docs/privacy.md` documentation.

## 11. Keyboard Combat

Every eligible key-down edge triggers a strike animation. Special keys: Space = big kick, Enter = uppercut, Backspace = block/recoil. Modifier-only events = no strike.
